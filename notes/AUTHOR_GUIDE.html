作者指南

写任何一页之前，先读完 00-design.md，找到你负责的节点的内容提要和它的前置节点。本指南是硬性规则；与本指南冲突时以 specs/task-spec.md 为准。

1. 文件与页面结构

每个知识点一个文件夹，例如 05-inverting-amp/，里面只放四个页面和一个图片文件夹：

05-inverting-amp/
├── page1.md      直觉篇
├── page2.md      原理与实现篇
├── page3.md      参数与调试篇
├── page4.md      动手实验篇
└── img/          本节点的全部 PNG（由脚本生成，不手工放图）

画图和仿真脚本放在 code/，文件名以节点编号开头，仿真脚本放 code/NN_*.py（例如 code/05_sim.py），画图脚本放 code/figs/NN_figs.py（例如 code/figs/05_figs.py）；共用模块 figstyle.py、schem.py 也在 code/figs/。

每页的固定结构：

  • 第一行是一级标题，格式为「NN 电路名 · 直觉篇」（或「原理与实现篇」「参数与调试篇」「动手实验篇」）。

  • 标题下面一行写导航：上一页、本节点其余三页、下一页，以及前置节点的链接。上一页、下一页按 README 的阅读顺序排：节点内 page1 → page4，page4 的下一页是下一个节点的 page1，下一个节点 page1 的上一页是本节点 page4；全书第一页 01 page1 的上一页和最后一页 45 page4 的下一页都是 README（第二部分 30–45 分批上线，下一个节点还没发布时，page4 的下一页按下一条的「即将上线」写法处理）。正文里提到「下一页」「下一篇」时要与导航一致。

  • 跨节点链接一律写全名加篇名，格式 [NN 名称 · 篇名](../NN-slug/pageN.md)，例如 [02 运放入门 · 直觉篇](../02-opamp-basics/page1.md)、[下一页：04 自锁 · 直觉篇](../04-self-locking/page1.md)。名称照抄 00-design §5.1（30–45 见 00-design-part2 §5.1）（写「04 自锁」，不写「04 自锁电路」「自锁控制」），链接指向具体的 pageN.md，不指向文件夹。指向尚未发布节点的链接由发布者在发布前临时改成纯文字「NN 节…（即将上线）」，原链接记在 pending-links.md，对应节点上线时恢复；作者照常写链接即可。

  • 交叉引用必须是链接。正文里不写纯文字的「见 13 page2」「page3 会再讲」：跨节点写 [NN 名称 · 篇名](../NN-slug/pageN.md)，本节点内写 [NN 名称 · 篇名](pageN.md)；要指到某一节，就在链接后面写「第七节」「例 3」这样的文字。代码块里的注释可以写「见 03 page2」，因为代码里没法放链接。自查（只应剩下代码注释）： grep -nE '(^|[^/A-Za-z_-])page ?[1234]([^.0-9a-z_]|$)' */page*.md

  • page1 直觉篇：痛点引入（读者在什么场景下会需要这个电路）→ 生活类比 → 示意图或电路图 → 用一句话说出这个电路「做了什么」。

  • page2 原理与实现篇：先补最小必要知识（或链接到前置节点）→ 推导，每一步都先用中文说意思再写公式，并代一组数算一遍 → 一段逐行注释的最小可运行 Python 仿真 → 仿真输出图和讲解 → 渐隐式例题（完整示例 → 关键步骤留空 → 变体迁移）。

  • page3 参数与调试篇：每个元件参数的物理含义、常用取值范围，改变它以后波形或效果怎么变（最好配一张参数扫描图）→ 故障排查表 → 练习题。

  • page4 动手实验篇（第 8 轮新增，完整说明见设计目录里的 LAB_BRIEF）：让读者用面包板、万用表和不超过 12 V 的直流电源把电路真的搭出来、量出来，再和前三页的数字对照。固定十部分，依次是：

    1. 导航行（见上）；
    2. 「这次实验要验证什么」：一两句话，并链接到 page2 里对应的结论；
    3. ⚠️ 安全须知：只用 12 V 及以下的直流电；电解电容分正负；三极管、稳压管、电阻可能发烫，不要用手摸；接线、改线前先断电。涉及 220 V/380 V 的节点（13、25、04、11、15、27、07、23、28）只做低压替代版（12 V/24 V 线圈、小灯泡或 LED 代替市电负载，按钮代替真实开关），必须写明「不要接 220 V」、市电部分请电工做；23 的过零检测、28 的市电初级不做实验。用两节 9 V 电池串联得到 ±9 V 时，要提醒两轨之间实际相差 18 V；
    4. 器材清单，表格列「元件 | 型号或数值 | 数量 | 说明」，型号用页面里用过的、常见易买的，不写价格；
    5. 搭建步骤：编号步骤写清每个元件插在面包板哪一排、哪一列；配面包板俯视接线图「图 NN-p4-1」（matplotlib + figstyle 绘制，标出行号、列号和电源轨，导线颜色区分正负和信号，图前同样要有引导句），并链接到 page2 的电路图；
    6. 测量表，表格列「步骤 | 测什么 | 红表笔 | 黑表笔 | 挡位 | 应该读到 | 读不到时先查」。数值取 review/spice/NN.md 里的万用表范围；那里没有的，用 code/NN_sim.py 或 spice/NN/run.py 实际算出来，不准编造；
    7. 「没有示波器怎么办」：给出用万用表、LED 或手机观察的替代方法（把 RC 放大到秒级、用 LED 亮灭看振荡、直流挡读平均值等）；确实只能用示波器看的照实说，并引用前几页的图或另画「图 NN-p4-2」说明示波器上应看到的样子；
    8. 一段 Python：读者填入自己量到的电阻实际值和电源电压，代码算出应读到的数并与实测值比较，偏差超过 10% 时打印提示；开头照旧写 sys.path 两行，填一组示例实测值，必须能被 tools/run_blocks.py 跑通；
    9. 实验记录表（留空，列「实测值 / 计算值 / 偏差」）加 3 道思考题，答案折叠；
    10. 自测清单，3–5 条「我能……」。

    page4 正文不少于 1500 汉字（tools/count_cjk.py NN-slug/page4.md --min 1500），并且和其他页一样要通过 run_blocks.py、check_figs.py、check_github_math.py。

  • 故障排查表固定四列：

    现象 原因 怎么查 怎么改

  • 练习题至少 3 道，由易到难，最后一道是变体迁移题；答案放在 <details><summary>答案</summary> … </details> 里，<summary> 后空一行再写 Markdown。

  • 每页正文不少于 500 汉字（page4 不少于 1500 汉字），代码、公式、图注不计入。用 tools/count_cjk.py 检查。

  • 有两个变体的节点（13、25、18、24）两种变体都要讲，见 00-design 的内容提要。

2. 图的规则

  • 电路图用 schemdraw（通过 code/figs/schem.py），波形和曲线用 matplotlib（通过 code/figs/figstyle.py），全部输出 PNG。禁止 ASCII 图、手工截图和 Mermaid。

  • 图片由 code/figs/NN_figs.py 生成，存到 NN-slug/img/，文件名写成 NN_pX_k_含义.png，例如 05_p2_1_waveform.png。每张不超过 200 KB（figstyle.save 会自动压缩并检查）。

  • 图号写成「图 NN-pX-k」：NN 是节点编号，X 是页码，k 是本页第几张图，从 1 开始连续。例如 05-inverting-amp/page2.md 里的第 2 张图是「图 05-p2-2」。

  • 每张图三件套：

    1. 引导句：图前一句话告诉读者要看什么，例如「请看图 05-p2-1 里橙色曲线的峰值」。
    2. 图注：图下一行，格式为 *图 05-p2-1　反相放大的输入与输出波形*。
    3. 图后讲解：至少两三句，说明图里的现象和它说明了什么。

  • 文字讲到电路连接就要配原理图；面包板图旁边要有原理图和「对照看」段。 page4 的每张面包板接线图后面紧跟一张用 code/figs/lab_schem.py 画的原理图（文件名 NN_p4_k_schem_lab.png，节点旁标出对应的面包板孔位），再写一段以「对照看」开头的文字，把面包板上的孔位、导线和原理图里的元件、节点一一对上。

  • 颜色词必须与图一致。figstyle 的固定配色（Okabe-Ito 色盲友好色板）如下，正文里照抄这些颜色词：

    用途 figstyle 键 颜色词
    输入电压 \(V_i\) vin 蓝色
    输出电压 \(V_o\) vout 橙色
    第三条曲线 third 红紫色（点划线）
    反馈、基准电压 fb 蓝绿色（虚线）
    电流 cur 天蓝色
    故障、错误情形 bad 朱红色（带 × 标记）
    理想值 good 黑色虚线
    参考线、门限、0V、电源边界 ref 灰色点线

    page4 面包板图的导线图例和正文一律用简单色名（红、紫、绿、蓝、橙、黑），不用上表的「朱红、红紫、蓝绿」。

  • 坐标轴标签一律写成「量 / 单位」，例如「电压 / V」「时间 / ms」，用 figstyle.axlabels(ax, "时间", "ms", "电压", "V")。

  • 参考线（0V、 \(V_{CC}\) 、门限、t = τ 等）用 figstyle.ref_h / ref_v，统一为灰色点线。

  • 图上的每一个数字都必须由脚本打印到终端（figstyle.mark 会自动打印），正文引用的数值要与打印结果一致，不许凭估计写。

  • 关键结论要用 assert 断言，例如 assert abs(gain - (-10)) < 0.05，这样参数被改错时脚本会直接报错。

  • 正文只提本页的图号。tools/check_figs.py 会把「图 NN-pY-k」这种指向别的页的图号判为错误；要引用别页的图，写成链接加文字描述，例如「见 05 反相放大 · 原理与实现篇 的波形图」。

  • 答案图放在揭晓之后：练习题的答案图只能出现在 <details> 里面，或者出现在正文揭晓答案的那句话之后。

  • 用法示例：

# 不运行（示意：figstyle 和 schem 的典型用法）

schemdraw 0.23 注意事项

  • 施密特反相器是 schemdraw.logic.SchmittNot（在 logic 模块里，schemdraw.elements 里没有）。
  • elm.NFet / elm.PFet 不画体二极管，需要时自己加一个 elm.Diode；而且一定要显式写方向 .theta(…)，否则它会沿用上一个元件的方向，画歪。
  • 横着串在电源线上的 MOS 管（比如 LDO 调整管、高边开关）用 elm.NFet().theta(-90).reverse()：源极在左、漏极在右、栅极朝上。
  • schem.module(...) 画方框模块时要接 .theta(0)，否则会沿用前一个元件的方向。
  • 读元件引脚坐标用 .absanchors['gate'] 这类绝对坐标，不要用 .anchors（那是元件自身坐标系，旋转后就不对了）。
  • elm.Opamp 也会继承上一个元件的方向；放运放前先 .theta(0) 或者在 d.add 之前把方向调回来。

加粗的标点规则

  • 句末标点（。，、；：！？）和全角括号放在 ** 外面：写 **例 1：给 LED 选限流电阻**。、**练习 1**：，不写 **……。**、**练习 1：**。原因：闭合的 ** 前面是标点、后面紧跟汉字时，GitHub 不认它是闭合符，页面上会露出 **（**朱红色带×**的 这种以符号结尾的也一样，要改写成以文字结尾）。
  • 闭合 ** 前面不能有空格，开头 ** 后面也不能有空格：写 **重点**，不写 **重点 **、** 重点**。

5. GitHub 公式规则

md 要能直接在 github.com 上正常显示公式：

  • 行内公式用 $…$，块公式用 $$…$$。
  • 开头的 $ 紧跟中文、全角标点、字母或 - 时 GitHub 不渲染，前面要补一个空格（紧跟 ( 或 ** 时不用补）。全角标点后面也要补：写 电压， $V_o$，不写 电压，$V_o$。写完运行 tools/fix_inline_math_spacing.py 文件…（不带 --check 就是修复模式，直接改文件），再用 --check 确认没有遗漏。
  • GitHub 会吃掉 Markdown 转义，要改成 KaTeX 和 MathJax 都认识的写法：
    • \, \! \; \: 改成 \thinspace \negthinspace \thickspace \medspace；
    • \{ \} 改成 \lbrace \rbrace，\| 改成 \Vert，矩阵里的 \\ 改成 \cr；
    • < > * 改成 \lt \gt \ast；
    • 公式末尾的 \% 移到公式外面，写成 $…$%。
  • 含 \begin… 的整行 $$…$$ 要单独成段，前后各留一个空行。
  • 用 tools/check_github_math.py 检查：它会调用 GitHub 的渲染接口，统计源文件里的公式数和渲染出来的公式数，两者相等才算通过。加 --fix 会做上面那些等价替换。
  • 行内公式里的 < > 一律写成 \lt \gt，例如 $R_f \lt 2R_g$、$V_i \gt 0$（直接写 < 会被当成 HTML 标签吞掉）。
  • tools/check_github_math.py 会直接判失败的写法：公式里的 \%、\!、\,（分别改成公式外的 %、\negthinspace、\thinspace），以及开头 $ 前缺空格（包括紧跟全角标点的情况）。
  • check_github_math.py 的三个坑（复核时反复踩到）：
    1. 行内公式里不写 <：GitHub 会把 $a<b$ 里的 <b… 当成 HTML 标签吞掉，公式数就对不上。一律写 \lt（> 同样写 \gt）。
    2. 不写 \,：GitHub 先做 Markdown 转义，\, 会变成 ,，公式显示错位或整条不渲染。改成 \thinspace，或者干脆写普通空格。
    3. \% 会把公式弄断：$50\%$ 在 GitHub 上不渲染。把百分号移到公式外，写成 $50$%，或者整个数字不进公式。
  • <details> 答案里不写 $$…$$ 块公式（GitHub 在折叠块里渲染不稳定），改用行内 $…$，或者把式子拆成几行行内公式。
  • 图注里不写任何公式（$…$ 都不要），公式放正文：图注只写「图 NN-pX-k　这张图是什么」，要讲的关系式写在图前引导句或图后讲解里。
  • GitHub 手机 App 不渲染公式，这是平台限制，不用处理。
